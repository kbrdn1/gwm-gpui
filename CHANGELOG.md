## [Unreleased]

### Added

- A GPUI window that lists the worktrees of a repo through `gwm list --format=json`.
- The list stays live through gwm's daemon (`subscribe` → `worktrees.changed`). The app uses a daemon already serving the repo, or starts one and stops it on quit, and falls back to a single `gwm list`. A line above the list says whether it is live (#3).
- A look after Monocode Native: a glass window with its own title bar and the selected worktree's tile, a sidebar of worktrees grouped by branch age (name, branch, age, issue, PR, dirty, ahead/behind), the selected worktree's details in a recessed card, and a status bar that says whether the list is live. Keyboard and mouse selection (#5).
- `scripts/bundle.sh` builds an unsigned `gwm.app` with its icon. Launched from the Finder, the app takes the login shell's `PATH` to find `gwm`, and asks for a folder when it is given none (#8).
- Actions on the selected worktree, in its card: open it in an installed editor or terminal, found by its `.app` bundle and launched with `open -a`, and remove it through `gwm remove`, behind a native confirmation that says when uncommitted changes will be lost. The branch is kept. Since `gwm remove` falls back to a substring match, a fresh `gwm list` must first show the worktree's name alone on the selected path, or the app refuses and says why (#7).
- Create a worktree from the title bar's `+`, through `gwm create`: from an existing issue's number (with a type when its labels do not give one), from a type, an issue number and a description, or with a free name. The new worktree is selected once the list shows it. A refusal shows gwm's words; an unapproved `.gwm.toml` is refused, with how to approve it (`gwm trust add`), never bypassed, not even by a `GWM_ALLOW_BOOTSTRAP` exported in the shell the app was launched from, for `gwm create` as for `gwm remove` (#9).
- The selected worktree's card shows its pull request (open, draft, merged or closed, its title, how many of its checks passed) and its issue (open or closed, its title), read through `gwm status --json` off the UI thread, each time the worktree is selected and when the list shows another branch, issue or PR for it, never per snapshot; the last answer stays shown while it runs again. A click opens either in the browser, an `https://` link only. Without what gwm resolves through `gh`, the card says gwm returned no live state; a failure, or no answer within 30 s, shows gwm's words, never "none" (#10).
- A project picker on the sidebar's repo row, after Monocode's: the repos opened before, most recent first, the window's own checked, and "Open folder…". Several repos are followed at once, one per window, each with its own live list and daemon; one already open in a window, from any of its worktrees, brings that window forward, from the picker as from File > Open…. The app keeps the last 10 repos in `~/Library/Application Support/gwm-gpui/recent`, one per repo whichever worktree was opened, and hides those whose folder is gone (#11).
- A click on a repo in the project picker, or a folder picked through its "Open folder…", takes the place of the repo the window showed; with ⌘ held, it opens in a new window, as ⌘O and File > Open… do. A repo a window leaves is no longer followed: the daemon the app started for it stops then, and so does a closed window's, instead of running until the app quits. A daemon you started is left running (#17).
- A landing view when the app is launched with no repo to show, as from the Finder: the repos opened before, read from disk at launch, and "Open folder…", with the folder picker over it. A repo picked there takes the view's place in the window. Cancelling the picker no longer quits the app (#19).
- A picked folder that is in no git repo is refused instead of opening a window on its error: a sheet on the window that asked gives git's reason, says so when the folder is a bare repo, and its "Choose another folder…" reopens the picker. This holds for the landing view, the project picker's "Open folder…" and File > Open… (⌘O); the window keeps the repo it showed. A path given as an argument is still taken as it is, which is how a bare repo is listed (#19).
- The sidebar shows the agent sessions gwm matched to each worktree, from the list's `agents` field. A worktree's row names the agent of its most recent session and, while gwm calls that session `active`, says so where the branch's age is otherwise. The selected worktree lists its sessions under its row, the five most recent, each with its name and `active` or the age of its last activity, and counts the older ones. `active` is gwm's word, never the app's guess: it is shown on a live list, which gwm's daemon updates when the word changes, and a list that is not live shows the age of the last activity instead. The field is experimental in gwm's contract: one this build cannot read is said so on the worktree, with the reason on its card, and never takes the list down (#21).
- A "New" row at the top of the sidebar, after Monocode's: it opens the "New worktree" form, as the title bar's `+` does, and shows its shortcut, ⌘N. File > New Worktree does the same (#23).
- A filter for the sidebar: the magnifier at the right of the repo's name, or ⌘F, opens a field that narrows the worktrees shown to those whose row says the text typed, in its name, branch, issue, pull request or the agent of one of its sessions. A section with no match is not drawn, and the list says when nothing matches. The selection stays among the rows shown, up and down walk them from the field too, and Escape clears and closes the filter; the worktree you had picked is selected again then (#23).
- A "Working" panel at the bottom of the sidebar, after Monocode's: a count and a card per session gwm calls `active` in the repo, across its worktrees, with the session's name, its worktree and its agent; a click selects the worktree. It is shown on a live list only, and not at all when no session is active (#23).
