# gwm-gpui

App desktop native pour [gwm](https://github.com/kbrdn1/gwm-cli), en Rust sur GPUI (`gpui-pre`, snapshots de Zed). macOS uniquement pour l'instant.

## Stack & commandes
⚠️ `export PATH="$HOME/.cargo/bin:$PATH"` d'abord : un rustc 1.89 du profil nix peut passer avant rustup, qui lui suit `rust-toolchain.toml` (1.99.1 ; `gpui-pre` 0.3.11 exige ≥ 1.98).

- Build : `cargo build`
- Test  : `cargo test` (l'app et `gwm-client`) · `cargo test -p gwm-client` (la couche gwm seule, en quelques secondes, sans compiler GPUI). Les tests de `gwm-client` pilotent un vrai `gwm daemon` : `gwm` doit être sur le `PATH`, sinon ils échouent (exprès, ils ne se sautent pas).
- Lint/Format : `cargo clippy --workspace --all-targets --all-features -- -D warnings` (comme la CI : `--all-features` vérifie aussi l'example de capture) · `cargo fmt --all`
- Audit : `cargo audit --deny warnings` (lit `.cargo/audit.toml`)
- Run   : `cargo run -- <chemin-du-repo>` (par défaut le dossier courant s'il est dans un repo, sinon la vue d'accueil, le sélecteur de dossier par-dessus). `gwm` doit être sur le `PATH`.
- Bundle : `scripts/bundle.sh` → `gwm.app` non signé dans `$CARGO_TARGET_DIR/release/` (build `--release` : recompile GPUI, plusieurs Go). Icône dessinée depuis `assets/app-icon.svg` par `sips` + `iconutil`, rien hors de macOS. Lancé du Finder : `open <…>/gwm.app`, ou `--args <repo>`.

Premier build long (GPUI compile tout) : `nice -n 10 cargo build -j 4` pour ne pas saturer la machine.

Voir l'UI sans écran : `cargo run --example screenshot --features screenshot -- <repo> <out.png> [--row n] [--no-sidebar] [--keys "down down"] [--click x,y] [--cmd-click x,y] [--scroll x,y,dy] [--wait ms] [--live ms]`. `--landing` à la place de `<repo>` ouvre la vue d'accueil (sans `--row`, `--no-sidebar` ni `--live`, qui sont pour un repo). `--keys`, `--click`, `--cmd-click` (⌘ tenu), `--scroll` (fait défiler de `dy` points ce qui est sous `x,y`) et `--wait` (laisse passer ce qui arrive hors du thread UI) passent par les vrais bindings et le vrai focus, se répètent et s'appliquent dans l'ordre donné (`--click` sur un champ, puis `--keys "4 2"` y tape) ; `--live` suit le repo comme l'app (thread `watch`, daemon lancé puis arrêté). Rend la fenêtre via `Window::render_to_image` (texture Metal, sans permission d'enregistrement d'écran). La feature tire le `test-support` de GPUI, jamais dans l'app ; la CI passe clippy en `--all-features` pour que l'example ne pourrisse pas. Le PNG garde l'alpha : le poser sur un fond (`magick fond.png rendu.png -composite`, fond en **sRGB**, un `gradient:` est en niveaux de gris et désature tout) pour juger. Le flou du window server n'y est pas.

## Structure
- `src/main.rs` : bootstrap de l'application (`PATH` du shell de login si `gwm` n'est pas sur celui hérité ; ce que montre le lancement, choisi par `open::start` : l'argument, pris tel quel, sinon le dossier courant s'il est dans un repo, sinon la vue d'accueil ; assets, touches, fenêtre, arrêt des daemons au `on_app_quit`). Tout le reste est en lib (`src/lib.rs` : `window_options`, `bind_keys` et ses liaisons, `bindings`, qu'un test résout par le keymap de GPUI ; `src/open.rs`), pour que l'example de capture ouvre la même fenêtre, de la même façon. Le menu File y porte « New Worktree » (⌘N) au-dessus de « Open… ».
- `src/open.rs` : ouvrir un repo (`open::repo`) ou un dossier choisi (`open::folder`) là où le dit une `Target` : `NewWindow` (⌘O, File > Open…, ⌘-clic dans le sélecteur) ou `Window(handle)` (clic simple : `replace_root` sur la fenêtre qui a demandé, qui garde sa place et sa taille). Un repo qu'une autre fenêtre montre déjà la fait passer devant ; celui de la fenêtre qui demande ne change rien ; une fenêtre fermée entre-temps laisse la place à une nouvelle. Y vivent aussi le lancement (`start` ; `landing` : la fenêtre sur la vue d'accueil, les repos récents lus sur disque hors du thread UI, puis le panneau d'ouverture par-dessus) et le sort d'un dossier choisi dans le panneau (`judge`, hors du thread UI : ouvert seulement si git le place dans un repo, sinon `refuse`, la feuille sur la fenêtre que donne `host`, une à la fois par fenêtre, `Sheets`). Logique sans fenêtre testée : `Target::of_click`, `plan`, `start`, `judge` (contre un vrai git : repo, dossier nu, repo bare), `host`, `Sheets`. Y vit enfin `Daemons`, la liste arrêtée au `on_app_quit`.
- Vues, un fichier chacune : `src/workspace.rs` (vue racine : état, sélection, cadre « rounded card » et ses coins peints), `src/title_bar.rs`, `src/sidebar.rs`, `src/detail.rs` (et ses actions : ouvrir dans…, supprimer), `src/open_menu.rs` (popover « Open in… »), `src/create_form.rs` (formulaire « New worktree » à la place de la carte, ouvert par la ligne « New » de la sidebar, ⌘N, File > New Worktree ou le `+` de la barre de titre), `src/text_input.rs` (champ d'une ligne, réduit de l'`examples/input.rs` de GPUI, Apache-2.0, voir `NOTICE` ; contexte de touches `TextInput`), `src/status_bar.rs`, `src/filter.rs` (le filtre de la sidebar : la loupe de son en-tête, le champ qu'elle ouvre, et `Query`, ce que la ligne d'un worktree doit dire pour rester ; contexte de touches `Filter`), `src/working.rs` (le panneau « Working » en bas de la sidebar : une carte par session que gwm dit `active`), `src/sessions.rs` (les sessions d'agents d'un worktree dans la sidebar : ce que sa ligne dit de la première, et les lignes imbriquées sous lui une fois sélectionné, sur un rail, d'après les rails de Monocode), `src/landing.rs` (vue d'accueil, racine de la fenêtre tant qu'aucun repo n'y est ouvert : la tuile de l'app, les repos récents et « Open folder… », les lignes du sélecteur de projet ; sans état, elle lit `Projects`). Logique sans fenêtre testée : `State`, `order`, `dismissed` et `removal_prompt` (workspace), `sections`, `children` et `child_of` (sidebar : `sidebar` dessine un élément par `Child`, donc sa position est l'index que prend le défilement, filtre appliqué), `Query` (filter), `working` (working), `mark`, `carried` et `lines` (sessions), `bindings` (lib), `src/age.rs` (format et groupes par jour, ceux de Monocode), `src/apps.rs` (éditeurs et terminaux installés, par leur bundle `.app` comme Monocode, ouverts par `/usr/bin/open -a`).
- `src/login_shell.rs` : le `PATH` du shell de login (`$SHELL -l -i`, valeur entre marqueurs, timeout de 5 s, groupe tué au-delà), pour un lancement Finder qui n'a que celui de launchd. D'après `scm/shell.rs` de Monocode.
- `scripts/bundle.sh` + `assets/app-icon.svg` : le `gwm.app` et son icône (tuile d'accent + branche ; ses couleurs recopient `theme.rs`, à changer ensemble).
- `src/project_picker.rs` : la ligne du repo en tête de sidebar, devenue bouton, et son menu (repos récents, « Open folder… »), après le sélecteur de projet de Monocode. Son état ouvert vit dans `window.use_keyed_state`, pas dans `Workspace`. Un clic dispatche `OpenRepo(chemin, Target)`, ou `OpenFolder(Target)` pour « Open folder… », traités dans `main.rs` par `src/open.rs` : clic simple, la fenêtre bascule sur ce repo ; ⌘-clic (`ClickEvent::modifiers().platform`), une nouvelle fenêtre. Un repo n'a qu'une fenêtre : celle qui le montre déjà passe devant. Ses lignes (`row`, `open_folder`) portent leur clic et servent aussi à la vue d'accueil ; le menu y ajoute sa fermeture.
- `src/recent.rs` : les repos récents, état de l'app et non de gwm : `~/Library/Application Support/gwm-gpui/recent` (ou le fichier que nomme `GWM_GPUI_RECENT`), une ligne `<common dir>\t<worktree ouvert>` par repo, 10 au plus, écrit à l'ouverture d'un repo hors du thread UI. Fichier absent ou abîmé = liste vide ; dossier disparu = caché, pas effacé. Lu au lancement (`listed`) quand aucun repo ne s'ouvre, pour la vue d'accueil : sinon c'est la première ouverture qui remplit la liste. Le global `Projects` y tient aussi quelle fenêtre montre quel repo (`show`, à chaque ouverture et à chaque bascule : un repo par fenêtre, une fenêtre par repo).
- `src/assets.rs` + `assets/icons/` : 8 glyphes Hugeicons (MIT) repris de Monocode, embarqués (`include_bytes!`), crédités dans `NOTICE`.
- `examples/screenshot.rs` : rend la fenêtre hors écran en PNG (voir commandes). `GWM_GPUI_RECENT=<fichier>` peuple le menu des projets, sans lire celui de l'app. Un clic sur un repo récent passe par `open::repo`, comme l'app : repo suivi en live (d'où `--wait`), et ce fichier réécrit. Un `--cmd-click` ouvre sa fenêtre à l'écran, rendue dans `<out>-2.png`. `--landing` ouvre la vue d'accueil, sans le panneau d'ouverture : « Open folder… » n'y fait rien, `OpenFolder` n'y est pas traité.
- `crates/gwm-client/` : tout ce qui parle à gwm, sans dépendance GPUI (workspace Cargo).
  - `src/lib.rs` : types du contrat, `gwm list --format=json`, `gwm remove` derrière sa garde (`removable`), `Repo::locate` (un seul `git rev-parse --show-toplevel --git-common-dir`) et `Repo::is_bare` (`git rev-parse --is-bare-repository`, pour nommer un repo bare dans un refus).
  - `src/agents.rs` : le champ `agents` d'une ligne de la liste (les sessions d'agents que gwm rattache au worktree : `top` et `sessions`, chacune avec `kind`, `freshness`, `last_activity`, `name` ; gwm donne aussi son `id`, non déclaré : rien ne le lit, et l'exiger rendrait toutes les sessions illisibles le jour où il change). Tier **expérimental** du contrat (« may change without a version bump ») : lu à part (`lenient`), `Worktree::agents` vaut `None` quand gwm n'a rien rattaché (champ omis, jamais `null`), `Some(Err(raison))` quand le champ est là sous une forme que ce build ne lit pas. Jamais une erreur de liste, ni sur `gwm list` ni sur le flux du daemon, où une sortie illisible mettrait fin au watch. `kind` reste une chaîne et `Freshness::Other` garde un mot inconnu tel que gwm l'a écrit.
  - `src/create.rs` : `gwm create` dans ses trois modes (`--issue [--type]`, triplet, `--name`), stdin fermé, jamais `--allow-bootstrap` ni `GWM_ALLOW_BOOTSTRAP` hérité (`writing_gwm` dans `lib.rs`, aussi pour `remove` ; le daemon n'y passe pas, ses méthodes ne lancent ni hook ni bootstrap) ; `Create::created` retrouve le worktree créé dans une liste (issue ou branche, chemin nouveau), jamais dans la sortie texte de gwm.
  - `src/status.rs` : `gwm status --json` (issue et PR d'un worktree, leurs champs live quand le `gh` de gwm les a résolus), lancé dans le dossier du worktree, stdin fermé. `issue` et `pr` requis (`null` sans lien) : leur absence est une erreur, pas « aucun ».
  - `src/daemon.rs` : le flux `subscribe` (contrôle de `schema_version`, handshake de 5 s) et le chemin du socket par défaut de gwm.
  - `src/watch.rs` : la stratégie : daemon du socket par défaut s'il sert ce repo (toplevel **égal** à un de ses worktrees, jamais un préfixe : un sous-module n'est pas son parent), puis socket propre à l'app, puis `gwm daemon` lancé par l'app, puis un seul `gwm list`. Une sortie illisible du daemon d'un socket partagé passe au suivant ; sur le socket propre de l'app, c'est une dérive de contrat, affichée. Si git ne localise pas le repo (bare), un seul `gwm list` : c'est gwm qui juge ce qu'il sait lister.
  - `tests/real_daemon.rs` : contre un vrai `gwm daemon` sur des repos jetables. `tests/real_remove.rs` : `remove` contre un vrai `gwm`. `tests/real_create.rs` : `create` contre un vrai `gwm` (`--issue` seulement là où gwm refuse avant la forge). `tests/real_status.rs` : `status` contre un vrai `gwm`, sur un repo sans remote (rien ne part sur le réseau).
- `src/theme.rs` : tokens : surfaces, opacités, rayons et tailles de Monocode Native (thème sombre, cadre rounded card), sauf l'opacité de la fenêtre, réglée sur ses captures (0.45 contre 0.85 par défaut chez lui, mesures dans le commentaire du token) ; accent (`ACCENT`, un seul token) et couleurs d'état de gwm (`claude-dark`).
- `.claude/rules/` : conventions path-scoped (`gpui-views.md`, `gwm-contract.md`).

## Conventions de code
- Rust édition 2024, 2 espaces, 120 colonnes (`rustfmt.toml`).
- La logique sans fenêtre se teste sous `#[cfg(test)]`, sur un échantillon réel de sortie gwm. Un changement de comportement arrive avec un test qui a échoué d'abord.
- L'UI se vérifie en lançant l'app, les tests ne voient pas un rendu cassé.

## Workflow Git
- Branche feature uniquement, jamais sur `main` directement, intégration dans `dev`.
- Worktree par défaut : `/me:issue-worktree-pr [desc]` (gwm). Variante checkout : `/me:issue-branch-pr [desc]`.
- Sprint : `/me:goal [desc]` (worktree autonome, merge progressif dans `dev`).
- Release : `/me:release [X.Y.Z]` — `/changelog` du repo → bump de `Cargo.toml` + `Cargo.lock`, commité sur `dev` → merge `dev` → `main` → tag **après** le merge → `gh release create --notes-file changelogs/<version>.md` (pas encore de CI de release). `changelogs/X.Y.Z.md`, sans `v`.
- Commits atomiques, Gitmoji + Conventional Commits, référencent l'issue.
- Issue remplie depuis `.github/ISSUE_TEMPLATE/*`, PR depuis `.github/PULL_REQUEST_TEMPLATE.md`.
- Review par défaut : boucle `/me:loop:claude-review-pr` (agent Claude frais, depuis le worktree). PR sensible : `/me:loop:codex-review-pr` (reviewer tiers). `/me:check-reviews [PR#]` à la main en second plan. `/me:loop:ci-until-green` avant merge.

## Notes spécifiques
- 🔴 **gwm reste la source de vérité** : aucune logique de worktree ici. Pas de dépendance Cargo sur `gwm-cli` : son `[lib]` est un point d'accès interne pour ses tests, hors SemVer. Lectures par le JSON gelé (`docs/schema/` de gwm-cli) ou le daemon JSON-RPC, écritures par un subprocess `gwm`. Détail : `.claude/rules/gwm-contract.md`.
- Une fonctionnalité qui demande un changement de contrat se fait d'abord dans gwm-cli.
- Daemon : gwm le documente comme lancé par l'utilisateur, un par repo, sur un socket par défaut partagé. L'app le lance quand même s'il manque, sinon la liste ne serait pas live, sur `<base>/gwm-gpui-<fnv1a du common dir git>.sock`, `<base>` étant celle du socket par défaut de gwm (`$XDG_RUNTIME_DIR`, sinon `$TMPDIR`) : un par repo, quel que soit le worktree ouvert, et l'arrête quand la vue qui le suit s'en va (fenêtre fermée, ou basculée sur un autre repo) et au `on_app_quit`. Tuée au lieu de quittée, elle laisse le daemon tourner : le lancement suivant le réutilise sans le posséder, il tourne jusqu'à un arrêt à la main. Le daemon ne passe pas par le trust ledger de `.gwm.toml` : pas de `--allow-bootstrap`.
- Fin d'un watch : `watch` ne rend la main que quand `on_event` répond `false`, et cherche un daemon 1 s après avoir perdu le sien. Arrêter son daemon seul lui en ferait donc lancer un autre. Le `Drop` de la vue (`Watch`, dans `src/workspace.rs`) lève d'abord le drapeau que teste `on_event`, puis arrête le daemon, hors du thread UI ; et `watch` arrête lui-même le daemon qu'il a lancé quand il se termine (celui qui démarrait pendant l'arrêt). Un daemon que l'app n'a pas lancé (celui de l'utilisateur sur le socket par défaut, celui qu'une app tuée a laissé sur le socket propre) n'est jamais arrêté : le thread du watch reste alors bloqué sur son flux jusqu'au prochain changement du repo, et ne se termine qu'à ce moment. Un thread par fermeture ou bascule, tant que le repo ne bouge pas.
- Manque du contrat, gardé ici et remonté (kbrdn1/gwm-cli#717) : pas de remove par chemin, et `gwm remove <motif>` retombe sur une recherche par sous-chaîne quand le nom ne résout rien (`auth` supprimé ailleurs → `auth-v2`). Juste avant de supprimer, `gwm_client::remove` relance `gwm list` et exige le nom seul sur le chemin sélectionné, id d'aucun autre, ni main ni le worktree où l'app a été ouverte (gwm et son daemon y tournent), et refuse si le worktree a des changements non commités alors que l'alerte confirmée le disait propre. Une seule suppression à la fois : gwm résout par nom, contre une liste qui peut encore montrer celle en cours. La vue le tient (`State::removing`), et `gwm_client::remove` aussi, par un verrou du process pris de la liste au retour de gwm : une fenêtre qui bascule sur un autre repo puis revient a une vue neuve, qui ne sait rien de la suppression en cours.
- Manques du contrat, remontés et non contournés dans gwm-cli : aucune méthode ne nomme le repo d'un daemon (on compare les chemins du premier snapshot ; kbrdn1/gwm-cli#730), aucune commande ne donne le socket par défaut résolu (la résolution est recopiée dans `daemon.rs` ; kbrdn1/gwm-cli#731), `subscribe` n'a pas de réponse, le premier snapshot en tient lieu (kbrdn1/gwm-cli#730 aussi), et le flux n'a pas de heartbeat (kbrdn1/gwm-cli#732) : un daemon suspendu (Ctrl-Z) ou dont les scans échouent en boucle garde la connexion ouverte sans rien envoyer, et la liste reste affichée « live » alors qu'elle est figée (`stream_subscription` n'écrit qu'au changement, `src/daemon.rs:885-920` dans gwm-cli, et `next_subscription_push` avale un scan en échec, `:247-259`, au commit `741981da`). Depuis #21, un `active` figé en fait partie (kbrdn1/gwm-cli#732 aussi). `gwm status --json` avale les échecs de `gh` (exit 0, champs live absents) : une panne GitHub s'affiche comme « no live state from gwm », pas comme une erreur (kbrdn1/gwm-cli#718).
- Dossier hors repo : un dossier choisi dans le panneau d'ouverture (⌘O, File > Open…, « Open folder… » du sélecteur ou de la vue d'accueil) que `Repo::locate` ne place dans aucun repo n'est pas ouvert. Une feuille (`Window::prompt`) sur la fenêtre qui a demandé donne la raison de git, et son « Choose another folder… » rouvre le panneau ; la fenêtre reste sur ce qu'elle montrait. Décision du mainteneur (#19) : pour un dossier choisi, c'est `Repo::locate` qui tranche ; gwm reste juge de ce qu'il liste pour un argument de ligne de commande, qui n'est pas jugé, pas plus qu'un repo récent. Un repo bare choisi est donc refusé lui aussi, et la feuille le dit bare, avec ses deux entrées : un de ses worktrees, que git place, ou l'argument. GPUI n'a pas d'alerte sans fenêtre et `NSOpenPanel` ne prend que le libellé de son bouton : c'est la vue d'accueil qui donne une fenêtre à la feuille au lancement Finder, et le panneau annulé la laisse ouverte (l'app ne quitte plus). `Window::prompt` n'est pas rappelé sur une fenêtre dont la feuille est encore ouverte : un second refus y attend la réponse au premier.
- `gpui-pre` vient de crates.io, **non modifié**. Monocode Native maintient une copie patchée de GPUI dans `vendor/` ; ce qui en dépend et manque ici (décision du user, ne pas vendorer sans lui) :
  - le matching de graisse (`vendor/gpui-pre-apple/src/text_system.rs` chez Monocode) : **vérifié**, `MEDIUM` rend au pixel près comme `NORMAL` dans SF, seul `SEMIBOLD` s'épaissit. Les titres de section sont donc en Regular ;
  - les fondus de bord (liste de la sidebar, libellé d'onglet ; `metal_renderer.rs`) : ici, des ellipses ;
  - le masque de coins de la carte : remplacé par des chemins remplis de wash (`card_corners`), comme Monocode hors macOS ;
  - le repositionnement Auto Layout des feux (`traffic_lights.rs` chez Monocode) : ici `traffic_light_position` seul.
  Images et détail : `docs/gpui-gaps.md`. Pas de manque, vérifié : le mélange alpha non patché donne bien du source-over sur les fonds empilés (alpha mesuré 0.859 = 0.85 + 0.05 × 0.15), et le `Blurred` de `gpui-pre-macos` 0.3.11 utilise déjà le matériau `UnderWindowBackground` (`src/window.rs:3947`) que Monocode a dû patcher sur sa 0.3.9. Le flou lui-même vient du window server et ne se voit pas hors écran : à juger en lançant l'app.
- Monocode est sous MIT : copier du code ou des assets impose son attribution dans `NOTICE`.
- Le panneau des fichiers modifiés de Monocode n'a pas d'équivalent : `gwm status --json` donne `branch`, `issue` et `pr`, aucune liste de fichiers. Demandé dans gwm-cli (kbrdn1/gwm-cli#712), pas simulé ici.
- PR et CI de la carte : `gwm status --json` lancé avec `current_dir` = le worktree (jamais `--worktree <nom>` : les patterns sautent le worktree principal). Lent (gwm appelle `gh`) : à chaque sélection d'un worktree (la dernière réponse reste affichée pendant ce temps) et quand le `branch`/`issue`/`pr` de la liste change ; jamais par snapshot ; un seul à la fois, tué (groupe de process, `gh` compris) après 30 s. Seul un lien `https://` s'ouvre : l'URL vient de la forge. Le contrat ne donne que `checks_passed`/`checks_total` : moins de passés que lancés est jaune (en échec ou en cours, le contrat ne dit pas lequel).
- Sessions d'agents (`agents`, tier expérimental, #21) : tout ce qui s'affiche est à gwm. `freshness` est son mot, jamais recalculé ici depuis `last_activity` (ce serait recopier sa règle des 300 s et faire passer une déduction de l'app pour son mot) ; `last_activity` est son horodatage, affiché en âge compté depuis lui (`Ages::since`), pas depuis l'arrivée du snapshot. Ce que fait le daemon, lu dans gwm-cli (lignes au commit `741981da`) et vérifié sur un vrai daemon 1.11.0 : `worktrees.changed` porte `agents` (mêmes lignes que `gwm list`) ; `worktrees_differ` compare `agents` en entier, `last_activity` compris (`src/daemon.rs:208-231`) ; `freshness` est reclassé contre l'heure courante à chaque poll (`src/json_api.rs:324`, `:336-339`, `:123`), donc le passage `active` → `idle` au bout des 300 s est poussé dans le tick (1 s par défaut) ; la détection elle-même est en cache 30 s (`src/json_api.rs:366`), donc une session qui apparaît, disparaît ou reprend se voit jusqu'à 30 s plus tard. L'app ne poll donc ni `gwm list` ni `gwm agents`. Limites, dites et non contournées : sur une liste non live (`Source::Once`, `Source::Lost`), le mot a l'âge de la liste, donc `active` n'est pas affiché, seul l'âge de la dernière activité l'est (`sessions::mark`) ; et un daemon suspendu ou dont les scans échouent ne pousse rien (pas de heartbeat, voir plus bas) : un `active` peut alors rester affiché au-delà de ses 300 s sur une liste dite « live ». gwm dit aussi `idle` une session terminée (process mort, fin enregistrée), même avant 300 s. Vu aussi : une session qui orchestre des sous-agents sans écrire elle-même dans ses artefacts est `idle` pour gwm.
- Sessions dans la sidebar, pas sur la carte : la ligne du worktree porte sa session `top` (le `kind` en texte au bout de la seconde ligne ; `active` à la place de l'âge de la branche sur la première, comme « Working… » remplace l'heure dans la ligne de Monocode, `session_suffix`), et les sessions sont des lignes imbriquées sous le worktree **sélectionné seulement**. Monocode ouvre un rail tant que son fil est en vue, choisi ou au travail, sur sa propre connaissance d'une réponse en cours ; l'`active` de gwm est une fenêtre de 300 s sur le dernier artefact écrit : seul « choisi » se transpose. Les 5 plus récentes sont listées, les autres comptées (`LISTED`). Une ligne ne nomme son `kind` que si les sessions du worktree ne sont pas toutes du même. Elles ne sont pas interactives (l'app ne peut rien faire à une session : lecture seule, ni `attach` ni `detach`) et restent dans l'enfant de liste de leur worktree, donc `child_of` et haut/bas ne les voient pas. Les lignes n'ont donc plus toutes la même hauteur : sélectionner un worktree replie les sessions de celui qu'on quitte, et un clic révèle sa ligne comme le clavier (`Workspace::select`), sinon un rail replié au-dessus d'elle la sortirait de la vue. Elle bouge quand même sous le curseur. La carte ne dit que ce que la sidebar ne peut pas loger : la raison d'un `agents` illisible.
- Ligne « New » et raccourcis (#23) : la ligne de navigation de Monocode (`sidebar_navigation`), son glyphe, le mot, le raccourci à droite. ⌘N, la touche de macOS pour File > New ; ⌘T, celle qu'affiche Monocode, y est un nouvel onglet, et cette fenêtre n'en a qu'un. La ligne écrit la touche réellement liée (`shortcut(NEW_WORKTREE_KEY)`, la constante de la liaison), jamais un texte recopié. `open_form` ouvre ou redonne le focus, sans refermer (le `+` de la barre de titre, lui, bascule), et ne fait rien tant qu'aucune liste n'est affichée. File > New Worktree est l'action du workspace : grisée sur la vue d'accueil, qui n'a pas de repo où créer.
- Filtre (#23) : ⌘F (la touche de macOS pour chercher dans une fenêtre ; ⌘K, celle de Monocode, ouvre sa recherche globale) ou la loupe ouvre un champ sous l'en-tête et lui donne le focus ; la loupe, champ ouvert, ou Escape le vide et le ferme. Un worktree reste si le texte se trouve, sans casse, dans ce que dit sa ligne : nom, branche, issue (`#21`), PR (`PR 22`), ou le `kind` d'une de ses sessions ; jamais le `name` d'une session (le prompt de l'utilisateur). Une section sans correspondance n'est pas dessinée ; sans aucune, la liste le dit (`Child::NoMatch`) et la carte aussi. **Règle de la sélection** : le worktree sélectionné est toujours une des lignes montrées. `State::selected` (le champ) est le dernier choix de l'utilisateur, `State::selected()` ce qui est sélectionné : ce choix s'il est montré, sinon la première ligne montrée, sinon rien. Le filtre ne déplace donc pas le choix : le vider le rend, sauf si une autre ligne a été choisie entre-temps (clic, haut/bas ; une touche qui ne déplace rien, haut sur la première ligne montrée, ne choisit rien, `State::step`). Haut et bas parcourent les lignes montrées, depuis le champ aussi : la liaison `Filter > TextInput` y prend le pas sur celle du champ (qui, dans le formulaire, déplace le curseur). Le champ n'a ce contexte que formulaire fermé (`filter::context`) : formulaire ouvert, la sélection est derrière lui et ne bouge pas (`Workspace::step`), et les deux touches seraient mortes ; elles redeviennent celles du champ. Un choix fait hors de la liste et que le filtre cache (worktree qu'on vient de créer, carte du panneau « Working ») vide le filtre, champ laissé ouvert (`show_selection`, `State::hides_selection`) : ce qu'on vient de sélectionner doit se voir. Escape ferme d'abord ce qui a le focus (`dismissed`) : le champ du filtre, sinon le formulaire, sinon un filtre resté ouvert ; fermé depuis son champ, le filtre rend les touches au formulaire s'il est affiché (son premier champ), sinon à la liste. Fermer la sidebar ferme le filtre : une liste réduite hors de vue déciderait encore de ce qu'atteignent haut et bas. Le panneau « Working », lui, n'est pas filtré. Limites, dites et non contournées : la ligne qui tient lieu de sélection sous un filtre compte comme une sélection pour `gwm status` (`begin_links` suit `State::selected()`), donc taper peut en lancer un pour une ligne qu'on n'a pas choisie, un seul à la fois comme au clavier ; et un formulaire qui se ferme (clic sur une ligne, `+`, création réussie) rend toujours les touches à la liste, même quand elles allaient au champ du filtre, qui reste affiché sans les recevoir.
- Panneau « Working » (#23) : en bas de la sidebar, d'après `shell/live_agents.rs` de Monocode : un en-tête (point, mot, compte) puis une carte par session que gwm dit `active` dans ce repo, tous worktrees confondus, dans l'ordre de la sidebar puis celui de gwm. Une carte dit le nom de la session, son worktree et son `kind` ; un clic sélectionne ce worktree. gwm ne donne ni l'outil en cours, ni le temps de travail, ni le modèle : les lignes que les cartes de Monocode ont pour eux n'existent pas ici, et rien ne les remplace. **Règle du panneau**, celle des lignes : il n'existe que sur une liste live (`State::live`), et sans session `active` il n'est pas dessiné, sans cadre vide. Un `freshness` inconnu n'est pas pris pour `active`. Un `agents` illisible n'ajoute aucune carte ; quand le panneau est dessiné, il compte à part les worktrees dans ce cas, sinon son compte passerait pour celui du repo. Une carte est une session telle que gwm la liste sous un worktree : une session rattachée à plusieurs (lancée dans l'un, épinglée par `gwm agents attach` sur un autre) a une carte sous chacun, comme chacune de leurs lignes dit `active`. Les compter pour une demanderait l'`id` de la session, que l'app ne lit pas (#21), et la liste ne dit pas dans lequel elle travaille. Au-delà de quatre cartes, la liste défile, la moitié de la cinquième visible (Monocode replie derrière « N more »). Ont été laissés hors de l'app, faute de fonction ici : les lignes « Inbox » et « Notes » de Monocode, le menu « … » de l'en-tête, le bouton de filtre à côté d'un titre de section, le rail de projets sous le panneau.
- Pas de logo de marque : Monocode embarque `claude.svg`, `codex.svg`, `opencode.svg`, marques de tiers, non recopiées dans ce dépôt public. Un seul glyphe neutre (`bot` de Hugeicons, `assets::AGENT`) vaut pour « une session d'agent », et le `kind` est en texte. Un glyphe par agent demanderait des marques que l'app a le droit d'embarquer (une licence de chaque éditeur, ou des glyphes neutres distincts à dessiner), et une correspondance `kind` → glyphe avec repli pour un `kind` inconnu.
- 🔴 Vie privée : le `name` d'une session est le prompt de l'utilisateur, son `id` et les chemins identifient sa machine. Rien de cela dans le dépôt, une issue, une PR ou un commit. Les tests lisent une vraie sortie gwm dont seules ces valeurs sont remplacées ; les PNG d'un repo aux vraies sessions restent hors du dépôt.
